# Account-backed daily progress

Rebuzzle should remember the fun parts of a player's daily journey when they reinstall or move to another device. A signed-in account can restore XP, weekly progress, streak-adjacent milestones, and badges from the server. Puzzle journal notes, saved artwork, answers, and explanations remain on the device.

The game stays a once-a-day puzzle. Progress is a friendly record of play, not a leaderboard, paid advantage, or punishment for missing a day. Daily play, hints, sharing, XP, weekly goals, and badges remain free; the existing Plus purchase stays separate.

## Player behavior

- The Journey screen shows account-backed lifetime XP, level, badges, and this week's completed puzzle dates. A short offline state shows the last synchronized snapshot and offers retry when sync fails.
- A guest's progress is stored against the server guest identity on that installation. Settings offers a native “Create account” flow that upgrades that guest in place, preserving the identity and its progress so the player can sign in on another device later.
- Signing in to an already existing account does not silently merge guest records. Before switching from a guest, explain that creating an account preserves this guest's journey, while signing in restores the selected account's journey. Keep the existing guest journal on-device and namespaced to the identity that created it, so changing accounts cannot expose those notes.
- Show a clear saved-state label: account-backed for a member, and “On this device” for a guest. Do not imply a guest's history can be restored after losing that device.
- The local puzzle journal remains device-only and namespaced to its owning guest/account identity. Sync no notes, guess text, answer text, explanation, illustration, or free-form journal content.

## Progress rules

- Only a server-persisted final attempt for the official daily puzzle creates progress. A correct final attempt is `solved`; exhausting all allowed guesses is `failed`. The game reveals the answer after that loss, but there is no separate voluntary reveal action or reveal outcome in the current API. Both completed outcomes earn the 25 XP finish reward and count toward the weekly goal. An unplayed or expired day has no progress record and earns nothing. Archive puzzles and non-final attempts never create daily rewards.
- The server derives the account ID from the verified bearer token and takes the puzzle ID, local puzzle date, final outcome, attempt count, and completion time from the accepted persisted attempt. `outcome` comes from `isCorrect`; `attempts` comes from the server-assigned terminal `attemptNumber` (solves are 1–3 attempts; a failed terminal session follows all three guesses); and the universal `completedAt` timestamp comes from server-created `attemptedAt` because the stored `completedAt` field is absent for losses and uses a separate clock read for wins. It ignores client-supplied user IDs, dates, outcomes, and XP.
- Materialize one minimal record per authenticated user and server-assigned puzzle date. A unique compound index and insert-only upsert make retries, simultaneous devices, and restore flows award a day once.
- The record contains only Journey inputs: puzzle ID, puzzle date, `solved`/`failed` outcome, attempt count, hint count, completion time, and the time zone used to obtain the daily puzzle. `timeZone` comes from the attempt's persisted `puzzleTimeZone` and is `null` for historical rows that lack it; never infer historical attempt zones from mutable stats. `hintCount` preserves the existing clamped, nondecreasing `hintsUsed` value on the persisted attempt; it is a best-effort client-reported signal, not proof that a hint was viewed. It is a nonnegative integer for new completions and explicitly `null` when legacy records do not contain hint history; a missing value is never treated as zero. It contains no raw guesses or journal content.
- Preserve the existing Journey scoring: 25 XP for any completed session, +75 for solving, +25 for a first-guess solve, and +25 for a solve with a reported zero hints. Levels continue to require 300 XP. Weekly progress counts three distinct completed official puzzle dates in the Monday–Sunday week, through today; a completed loss counts as a finish. Existing badge thresholds remain first finish, first-guess solve, three solves with a reported zero hints, and seven finishes.
- A saved puzzle date is immutable. Store a stable `journeyTimeZone` on every identity, including guests, as an account field; do not reuse mutable `UserStats.streakTimeZone`. Initialize it at guest/account creation or guest upgrade when the valid IANA zone is available; otherwise initialize once on the first authorized daily-puzzle or progress request. Legacy identities first use the newest valid persisted daily-attempt `puzzleTimeZone`, then the valid request zone, then UTC. The request resolver prefers the existing `rebuzzle-tz` cookie, then an explicit `x-rebuzzle-time-zone` client header, then `x-vercel-ip-timezone`, then UTC. Use an atomic set-if-absent so simultaneous first requests cannot pick different zones. After initialization, a device time-zone change or another device's header never changes it; a later explicit time-zone preference is out of scope. Every official daily-puzzle retrieval path uses this stable zone for the local puzzle date, puzzle selection, and daily lock, so the same identity receives one official puzzle date across devices. Finalization and restore use the date and zone from the accepted persisted attempt, never the current request header. New terminal attempts persist that effective zone as `puzzleTimeZone`. Historical attempts have no recorded time zone; keep their original `puzzleDate` and represent their unknown `timeZone` as `null` rather than inferring from current stats or rewriting dates. The API uses the stable account zone to compute `asOfPuzzleDate`, `currentWeekStart`, and `currentWeekEnd` for a Monday–Sunday week. Clients do not independently decide which week is current. Settings explains that the daily reset follows the saved account time zone.
- Before release, a resumable, idempotent server-side backfill walks existing persisted final daily attempts in keyset-paginated batches, materializes the projection, and writes a completion marker only after the full scan succeeds. It records batch counts and a terminal completion status for operational verification. Large histories do not block a user's progress screen or appear as a zeroed Journey while migrating. The client cannot claim historical completions. If old attempts lack hint metadata, they can support finish/solve/attempt rewards but cannot be counted as verified unassisted solves.
- If saving the projection fails after a final attempt was accepted, a retry or session restore must idempotently reconstruct it from that saved final attempt. For concurrent `$setOnInsert` upserts that race on the unique index, catch duplicate key, read the winning row, and treat it as success. The client can show a pending sync state until the server confirms.

## API and storage

- Add an authenticated `GET /api/user/progress` response with the computed Journey summary, recent date entries, server-anchored week bounds, and per-user backfill status. Its JSON shape is `{ asOfPuzzleDate, currentWeekStart, currentWeekEnd, summary, recentEntries, backfill: { status } }`. `backfill.status` is one of `not_started`, `in_progress`, `complete`, or `failed`, scoped to that user. When status is not `complete`, `summary` is `null` and `recentEntries` is empty; the client uses the same identity's last-synced snapshot or shows syncing/unavailable. For `complete`, `summary` is `{ totalXP, level, xpIntoLevel, finishes, solves, firstGuessSolves, unassistedSolves, completedThisWeek, badges }`, with every count a nonnegative integer, `level` a positive integer, and `badges` an array of stable IDs from `first-finish`, `first-guess-solve`, `three-unassisted-solves`, and `seven-finishes`. `recentEntries` contains every completed entry in the current week plus up to the 35 most recent completed entries with `puzzleDate` before `currentWeekStart`, shaped as `[{ puzzleDate, puzzleId, outcome, attempts, hintCount, completedAt, timeZone }]`; the weekly goal uses the server's `completedThisWeek` and does not require a duplicate date array. New accounts with no older final attempts are immediately `complete`; an unrelated user's backfill never blocks them. The response is scoped to the bearer-token user; no user ID query parameter is accepted.
- Add `journeyTimeZone` to the account identity and `puzzleTimeZone` to new persisted puzzle attempts; historical attempts keep that field unknown. Add a central Mongo `dailyProgress` collection definition and a unique `{ userId, puzzleDate }` index. The write operation accepts a verified persisted final attempt and uses `$setOnInsert`/upsert. Its `puzzleDate` is the accepted local daily key from the guess route, not UTC midnight; archive lock keys are excluded. Follow existing explicit index-creation operations; production auto-indexing is disabled by default.
- Record progress in the official daily finalization path. If the attempt is already persisted but projection writing fails, keep the accepted puzzle result successful and log the projection failure; reconcile from the persisted terminal attempt on session restore, progress fetch, or the resumable backfill. Guess retries after finalization return a conflict today and must not be treated as the only repair route. Keep `/api/user/stats` semantics unchanged; Journey XP is not the same as existing account points.
- Add `POST /api/auth/guest/upgrade`. It requires a valid guest bearer token, confirms the database identity is still a guest, applies the existing signup validation and password hashing, converts that same user record in place, and returns a member token. Never accept an arbitrary guest ID or rely on device ID alone as proof.
- Existing-account sign-in continues to switch to that account without transferring guest progress. Native copy explains this before the switch; this work does not build an account-merge product.
- Keep an account-keyed last-synced snapshot as an offline display cache. A member sees only that snapshot while offline; with no snapshot, show a truthful syncing/unavailable state rather than totals inferred from the private journal. The verified server response replaces the cache; cache failures never block a puzzle, a final answer, journal editing, or account sign-in. Guest progress can be shown from that guest's own server response/cache, with clear “On this device” portability copy.
- Guest-upgrade retries are idempotent after response loss: if the same verified guest token resolves to a user record already upgraded by the first request, require the submitted email/password to authenticate that exact user ID, then issue a fresh member token. Do not accept different credentials or create another user.

## Privacy, safety, and monetization

- Store the minimum data needed to render progress. Do not use puzzle history to send additional marketing, email, or push messages as part of this change.
- Keep hints, journal, and puzzle play available without purchase. Do not add paid streak repair, XP multipliers, or pressure copy. Missing a day does not erase lifetime progress or create a purchase prompt.
- A guest's anonymous server record is not portable by itself. Account upgrade changes that same server identity to a member; signing in to a different account does not merge the guest record. A guest upgrade preserves the guest's initial `journeyTimeZone`.
- Add the new progress data and guest-upgrade flow to the existing privacy documentation if the current data inventory does not already cover them. Verify the App Store privacy declaration matches actual storage and account-creation behavior.

## Acceptance checks

1. Finishing the same official daily puzzle twice, racing two devices, or restoring after an ambiguous response creates one progress record and awards XP once.
2. A non-final guess and an archive completion create no daily progress record; an unplayed day creates no `missed` record. A terminal failed attempt counts once as a completed day and earns only the finish reward; showing the answer after that loss does not create another outcome or reward.
3. The authenticated progress response cannot read or mutate another user's records, even when a client supplies another user ID.
4. Server outcomes, dates, and rewards come from accepted server attempts; client payload cannot create a win, change the date, or mint arbitrary XP.
5. A progress write failure can be healed from the persisted final attempt on retry/restore without double-counting; a unique-index race reads and accepts the winning record.
6. Creating an account from a guest keeps the same user ID and stable Journey time zone and restores the same Journey on another device; a lost upgrade response can be retried safely; signing in to an existing account does not merge the guest history or expose its journal.
7. Weekly dates, XP thresholds, and badges match existing Journey behavior; the private journal stays device-only and unchanged.
8. VoiceOver, Dynamic Type, reduced motion, dark mode, and offline/error/retry states remain usable.
